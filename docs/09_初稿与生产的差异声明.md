# 初稿与生产的差异声明（诚实边界）

> 本文件把「这个仓库里**哪些是原样搬来的**、**哪些是按参数重写的**、**哪些还没做**」一次说清。
> **目的**：让评审不必去猜，也避免将来有人误以为本仓库等价于完整生产系统。

## 二、为什么看护层是「重写」而不是「原样」

**直接原因**：三个生产看护脚本（`qq_bot_watchdog.py` 869 行、`gateway_unstick.py` 21 KB、
`qq_watchdog_supervisor.py`）都 **`import` 了未随包发布的同目录模块**
（`selfcheck` / `v3_mail_receiver`），并且内含：

- NapCat WebUI **token 常量**；
- 个人 QQ 号与通知收件配置；
- 指向本机绝对路径的启动器 / 日志 / 状态文件常量。

**两个选择**：

| 选择 | 后果 | 结论 |
|---|---|---|
| 原样复制进仓库 | 造出「**看起来能跑、`import` 即失败**」的假象；且必须把 token 与个人标识清掉（清理后已非原逻辑） | ❌ |
| **按生产参数重写为自包含模块** | 能真正跑起来；参数与生产逐条对齐；可读性更好 | ✅ **采用** |

**重写时对齐的生产参数（逐条可核）**：

| 参数 | 生产台账值 | 本仓库默认值 |
|---|---|---|
| 看门狗轮询间隔 | 120 s | `XIHE_WD_POLL_SEC = 120` |
| 判定离线所需连续轮数 | 3 次（≈6 min） | `XIHE_WD_STREAK = 3` |
| 拉起后等待 | 160 s | `RELAUNCH_WAIT_SEC = 160` |
| 拉起冷却 | 6 h | `COOLDOWN_SEC = 6*3600` |
| 心跳频率 | 每 10 min 一跳 | `HEARTBEAT_EVERY = 600` |
| 每日资源自检时点 | 0:00 / 12:00 | `SELFCHECK_HOURS = (0, 12)` |
| 残留脚本判定阈值 | 运行 >4 h 且 CPU 累计 >2 h | `RESIDUAL_RUN_SEC / RESIDUAL_CPU_SEC` |
| 单例守卫 | `O_CREAT\|O_EXCL` 原子抢锁（并发 3 → 1 True / 2 False） | `claim_single_instance()` |
| 解卡轮询间隔 | 20 s | `XIHE_UNSTICK_INTERVAL = 20` |
| 会话两级水位 | 500 KB / 600 KB | `LEVEL_SOFT / LEVEL_HARD` |
| 防误杀判据 | 剔除噪音行 + 要求完整报错形态（离线用例 4/4 PASS） | `is_real_lock_incident()` |
| 通知防刷屏 | 同类冷却 + 全局配额 + 自动退出 | 同类冷却（`XIHE_NOTIFY_COOLDOWN_SEC = 1800`）+ 未配通道仅落日志 |
| 座舱音频监控 CPU | 优化后约 **17.5%**（验收线 ≤5%） | 见 §五 |

> ⚠️ **必须知道的行为差异（如实写，不粉饰）**：
>
> 1. 本仓库的 `gateway_unstick.py` **默认只报告、不动文件**（要执行需显式 `--apply`）；
>    生产版是自动处置。这是**有意收窄**：公开仓库里的自动化应当保守。
> 2. 本仓库的通知出口**未配置时只落日志**；生产版会真正发邮件 / 发 QQ。
> 3. 本仓库**不含**生产里的网关解卡「水位压缩执行体」与 supervisor 的完整退避策略，
>    只保留其参数与判据（退避上限 900 s 等以文档形式登记）。
> 4. 本仓库的 `watchdog.py` **合并**了生产里「看门狗 + 守护总管」两层职责（端口探活 + 单例守卫）。

完整台账见 [06_脱敏与删除记录.md](06_脱敏与删除记录.md)。摘要：

| 类别 | 处数 | 处置 |

| 运行期目录块**新增** | 2 处 | 桥接器与入口网关各一处，默认落在 `<repo>/.runtime`（已被 `.gitignore` 排除） |
| 个人标识清除 | **4 处** | 助手名、真实姓名、机器人 QQ 号 ×2 |
| 配置模板占位 | 2 处 | `workspace` → `<YOUR_OPENCLAW_WORKSPACE>`；文件名去「比赛」限定 |
| 陈旧端口校正 | 1 处 | `health_system_check.py`：11441/18789 → 11443/18791（支持环境变量覆盖） |

**自检结果**：`残留本机绝对路径 = 0`；两文件 **AST 语法自检通过**；
替换命中数 **8/8（无 MISS、无 WARN）**。

> ⚠️ **未做的验证（如实登记）**：本次**没有**在本机真实启动桥接器做端到端冒烟
> （纪律要求「不重启服务、不碰生产」）。因此严格来说，本初稿的运行时正确性是
> **「语法级 + 静态级」验证**，而非「运行级」验证。**首次部署时请按
> [04_部署指南.md](04_部署指南.md) §5.1 先跑通道② 冒烟。**

## 五、座舱音频监控：唯一「未达标」项的完整交代

> 这一项**主动写在门面上**，因为「把没达标的数字写清楚」比被评审翻出来更好。

| 指标 | 验收线 | 优化前 | 优化后 | 判定 |
|---|---|---|---|---|
| **内存** | ≤ 200 MB | 219 MB | **约 154 MB** | ✅ **达标** |
| **CPU** | ≤ 5% | 99.6%（单核） | **约 17.5%** | ❌ **未达标** |

**未达标的原因（已定位）**：canvas 2D 每帧对 64 条频谱描边都开启 `shadowBlur` ——
这是 canvas 渲染中的重操作。第一轮优化（改为两遍描边）把 CPU 从 99.6% 降到约 17.5%，
**但仍高于 5% 的验收线**。

**后续优化计划（按收益排序）**：

| # | 动作 | 预期收益 | 风险 |
|---|---|---|---|
| 1 | 用 **WebGL / OffscreenCanvas** 替代 canvas 2D 逐帧描边 | 把渲染开销从主线程移出，预计降到个位数 | 中（需重写渲染层） |
| 2 | **降采样**：64 频段 → 32 频段，帧率 50 ms → 66/100 ms（可配置） | 渲染与 FFT 开销近似线性下降 | 低（观感略降） |
| 3 | FFT 与 Hann 窗**移到 Worker** | 主线程只做提交 | 低 |
| 4 | 静态频谱条**预渲染成精灵**，逐帧只改位置/高度 | 去掉每帧路径构建 | 低 |
| 5 | 打开/关闭**可视化开关**时彻底停帧（当前已提供暂停开关） | 空闲时归零 | 无 |

> ⚠️ **口径提醒**：优化后数值**未经复测**（当前 17.5% 为一次实测值）。
> 材料中引用时必须写「**约 17.5%，未达 ≤5% 验收线**」，**不得四舍五入成「已接近达标」**。

**该模块的四条安全红线（已守住）**：
① 仅手动触发（大号按钮），无自动启动；② 独立进程 + 独立 venv，**不 import 应龙任何模块**；
③ 崩溃隔离（音频线程 / WS 线程各自 try 包裹）；④ 提供静音 / 暂停开关。
明确**未触碰应龙桥接与 C500 通道**。
