## 二、为什么要「另起新仓」而不是在旧仓上瘦身

| 维度 | 复用 G1（比赛版老仓）❌ 否决 | **新建干净仓** ✅ 主路线 |
|---|---|---|
| 第一印象（评审点开仓库） | 702.6 MB / 0 star / 0 fork / 0 贡献者 / 旧定位简介 —— 「一眼看穿」类风险全留在原地 | 30–40 MB 级、门面新定位、topics 可检索、有 Release —— 第一眼是「活的项目」 |
| `.git` 历史巨物 | 🔴 只能靠 `filter-repo` 改写 12 个提交（**不可逆**） | ✅ **不继承**：新仓从 `git init` 开始，历史即「你放进去的东西」 |
| 旧仓 8 个 Issue 引用链 | 🔴 改写历史 → **全部断链**；开发记录里的 6 个 commit 号同时作废 | ✅ **零影响**（旧仓原封不动） |
| 安全脱敏 | 🔴 旧库历史深处沉着早期版本文件，**公开复用等于把历史整体再公开一次** | ✅ **白名单入场**：只复制该留的；脱敏是**进门检查**而不是事后补救 |
| 大二进制 | 🔴 仍在历史里（346 MB / 212 MB / 202.83 MB 已删巨物 + 112.87 MB PPT） | ✅ 全部改外链 / Release |
| 操作耗时 / 可逆性 | 1–2 天；**不可逆** | **半天内**；**完全可逆**（旧仓天然是备份） |

> **一句话**：旧仓 **702.68 MB 里有 77.28% 是 `.git`**，而 `.git` 的大头是**三大已删巨物（合计 771.7 MB）**。
> **删文件 ≠ 减体积** —— 要体积只有两条路：**另起新仓** 或 **改写历史**，没有第三条。

## 五、推送纪律（模板化，可复制给日后新仓）

```powershell
# 本地工作副本 = 白名单新建（❌ 不从旧仓 clone）
git push origin  main      # H：GitHub 主源，唯一上游
git push gitlink main      # G2：GitLink 平台镜像（单向）

# 主源若建不成：删掉 origin 一行，gitlink 升为唯一上游（内容与目录完全不变）

# 已封成脚本，从此不再手打两个远端：
pwsh scripts/push-all.ps1 -DryRun        # 先体检（含敏感信息扫描闸门）
pwsh scripts/push-all.ps1 -Message "..." -GitHubUrl "<H>" -GitLinkUrl "<G2>"
```

**每次推送后的 30 秒体检**（脚本已内置）：

```powershell
git remote -v                       # 确认 上游/镜像 的指向没搞反
git log --oneline -3
git count-objects -vH               # 本地体积，应远小于 100 MB
git status --short
```

### ❌ 明确不做

| # | 不做 | 原因 |
|---|---|---|
| 1 | 反向 `pull` GitLink → GitHub | 破坏单一上游 |
| 2 | 双向互镜像 | 会产生两套提交图与合并节点，两侧 README / Release 极易不一致 |
| 3 | 用平台的 "Import repository" | 会把旧仓 702 MB 历史整包带进来 |
| 4 | 改写 G1 历史 / 强推 / `filter-repo` | 会打断 8 个 Issue 引用链 |
| 5 | 把 G1 整体搬上任何新仓 | 等于把 702 MB 问题复制成两份 |
| 6 | 上 Git LFS | 瘦身后最大件是 MB 级；上 LFS 只增加 clone 门槛 |
