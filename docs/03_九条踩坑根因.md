# 九条踩坑根因（工程韧性证据）

> 这些坑**全部是真实发生并被记档、修复、复验过的**，不是设想。
> 在本项目里，它们与主线成果**同等价值**：评审能看到「问题被记录、被定位到根因、被修复、被复验」的工程习惯。
> 每条给出：现象 → 根因 → 修复 → 复验证据。

---

## 坑 1｜容器 `~/.ssh` 不持久 → SSH 免密方案每次重建都要重加公钥

| 项 | 内容 |
|---|---|
| **现象** | `root@<网关IP>: Permission denied (password)` —— 服务端只提供**密码**认证，未接受公钥 |
| **根因** | 私钥是在**旧容器**（`f8b7832a425d`）内生成的，公钥加在**旧容器的** `~/.ssh/authorized_keys`；**实例重启 = 容器重建 → `authorized_keys` 丢失** |
| **修复** | ① 改用**密码认证**打通；② 随后收敛为 **SSH 固定隧道**（`-i` 指定密钥 + 本地端口转发），不再依赖容器内免密配置 |
| **复验** | 隧道固定后本地 `18000 → 云端 8000` 长期稳定；`GET /v1/models` Open（10:42） |
| **可复用教训** | **容器化实例的 `~/.ssh` 不持久** —— 任何「配一次就好」的免密方案都要重新评估 |

## 坑 2｜平台只认密码认证 + authtoken 泄露（安全项）

| 项 | 内容 |
|---|---|
| **现象 A** | 平台 SSH 不接受公钥，只提供密码 |
| **现象 B** | **ngrok authtoken 在截图中暴露** |
| **根因** | A：平台侧认证策略；B：截图时未遮挡凭据画面 |
| **修复** | A：改用固定 SSH 隧道；B：**吊销并重新生成 authtoken**（09-16 完成） |
| **复验** | authtoken 已换新；公开证据集中**主动剔除含私钥画面的截图 1 张**（画面含 `id_ed25519` 全文，**禁止入公开仓库**） |
| **可复用教训** | ① 凭据一旦可能进画面，就按「已泄露」处理；② **截图入库前必须逐张核验凭据可见性** |

## 坑 3｜ngrok 免费版插浏览器警告页 → 不带请求头就 `ERR_NGROK_6024`

| 项 | 内容 |
|---|---|
| **现象** | 本地调用云端 32B 时，收到的是浏览器警告页而不是 API 响应 |
| **根因** | ngrok 免费版对**非浏览器 UA** 的请求插入警告页；脚本没带跳过头 |
| **修复** | 所有探活与请求统一带 **`ngrok-skip-browser-warning: true`** 头（桥接器里做成常量 `C500_EXTRA_HEADERS`） |
| **复验** | 带上头后 `chat.completion` 正常返回；不带头的失败过程**单独截图留证** |
| **可复用教训** | 隧道/网关的**插页行为**会让 API 返回 200 但内容不是 JSON —— 探活必须校验**响应结构**，不能只看状态码 |

## 坑 4｜vLLM 在容器内不稳定（曾掉线）+ 云端 EngineCore 孤儿占显存

| 项 | 内容 |
|---|---|
| **现象** | 运行中 vLLM 容器内进程掉线；重启后显存未释放 |
| **根因** | 容器内进程生命周期不受本机看护；EngineCore 孤儿进程残留占显存 |
| **修复** | ① 桥接器侧**探活兜底**（发请求前先探 `/v1/models`，缓存 30 s → 实例没开时秒级回落，不干等 180 s）；② 三重回落（不可达/超时/非 200 → 回落 ①）；③ 云端 `c500_guard.py` 5 分钟轮询监控；④ 看护 v1.3 把**判失联从 2 轮放宽到 3 轮**，避开 vLLM 重启加载窗口（≈85 s）的误报 |
| **复验** | 探活 + 回落链路实测生效；掉线场景截图留证 |
| **可复用教训** | 远端推理服务的**重启加载窗口**必须计入失联判定阈值，否则会误判并反复拉起 |

## 坑 5｜PowerShell 中文编码乱码

| 项 | 内容 |
|---|---|
| **现象** | 本地调用返回中文乱码（mojibake） |
| **根因** | 控制台/管道默认编码与 UTF-8 不一致（桥接器与 PowerShell 双方都可能出问题） |
| **修复** | 桥接器强制 `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1`，重定向 stdout 为 UTF-8；响应侧显式 `encoding='utf-8'`；调用侧显式 UTF-8 解码 |
| **复验** | 中文回复正常（「我是Qwen，由阿里云开发的大型语言模型助手。」）；乱码过程截图留证 |
| **可复用教训** | 中文链路上编码要**在每一跳显式声明**，不要依赖默认值 |

## 坑 6｜`orphan-self-pid` 会话写锁报错（跨 3 个版本排查）

| 项 | 内容 |
|---|---|
| **现象** | Windows 上 gateway 报 `SessionWriteLockStaleError: session file lock stale (orphan-self-pid): pid=XXX alive=true` —— **pid 是 gateway 自己且存活**；新建会话发消息 1-2 秒内必现，持续 1 天无法对话 |
| **排查过程** | 禁用 lossless-claw → 仍报错 → 降级 v5.4 → 仍报错 → **源码分析**：`getProcessStartTime(pid)` 在 `if (process.platform !== "linux") return null` → **Windows 永远返回 null** → 锁文件无 starttime 字段 → 判定 stale → 但**最终发现真正的触发链**是下一层 |
| **真正的根因** | 外部编辑器的 **safe-delete hook 通过环境变量注入到 gateway 子进程**，累计 **20 次**文件操作后触发 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`；gateway 无法应答交互式确认 → 会话文件写入阻塞 **44 秒** → 超时失败 → 触发 `orphan-self-pid` |
| **修复** | launcher 脚本启动前**清除所有 `SAFE_DELETE*` / `CODEBUDDY*` 环境变量**（见 [`../src/entry/launch_gateway.py`](../src/entry/launch_gateway.py)） |
| **复验** | v2026.6.9 + 清除环境变量后 **0 次复发** |
| **可复用教训** | ① 平台差异（Windows 上 `getProcessStartTime` 恒为 null）会制造**看似框架 bug** 的现象；② **继承环境变量**是最隐蔽的故障注入源 —— 启动器要主动清理 |

## 坑 7｜`protocol mismatch`：webchat 连不上 Gateway

| 项 | 内容 |
|---|---|
| **现象** | 升级后打开 webchat 持续报 protocol mismatch |
| **根因** | 升级后 WebSocket 协议从 **v3 升到 v4**，浏览器**缓存了旧版** webchat JS |
| **修复** | 强制刷新浏览器（`Ctrl+Shift+R`） |
| **复验** | 刷新后正常 |
| **可复用教训** | 前端资源版本与后端协议版本必须一起升级；文档里要写明「升级后强制刷新」 |

## 坑 8｜自动解卡助手**误杀自己**（把正常对话当成写锁卡死）

| 项 | 内容 |
|---|---|
| **现象** | 解卡助手把 agent **回复正文里出现的 `SessionWriteLock` 字样**误判为真实写锁卡死 → 触发误杀；误判延迟仅 **5 s** |
| **根因** | 判据是**裸关键词子串匹配**，没有区分「报错证据」与「对话内容引用」 |
| **修复** | ① 先**剔除噪音行**（对话 JSONL / 事件流 / 心跳）；② 再要求匹配**完整诊断报错形态**（而非孤立关键词）。见 [`../src/health/gateway_unstick.py`](../src/health/gateway_unstick.py) 的 `is_real_lock_incident()` |
| **复验** | 防误杀补丁**离线用例 4 组全 PASS** |
| **可复用教训** | 任何基于日志关键词的自动处置，都必须先做**「证据行 vs 内容引用」甄别**；「宁可不拉也不误拉」是本项目的默认取向 |

## 坑 9｜单例守卫非原子 → 双 watchdog 并存 16.4 小时

| 项 | 内容 |
|---|---|
| **现象** | 看护进程出现**两个实例并行**，真实并存时长约 **16.4 小时**（09-14 15:49 → 09-15 08:15） |
| **根因** | 原实现「读 pidfile → 判存活 → 返回」与后续写入之间存在**竞态**（非原子） |
| **修复** | 改为 `os.open(..., O_CREAT\|O_EXCL\|O_WRONLY)` 抢锁 —— Windows 上映射为 `CreateFile` 的 **`CREATE_NEW`** 语义，由**操作系统保证**「文件不存在才创建成功」；并含**陈旧锁自动接管**路径。见 [`../src/health/watchdog.py`](../src/health/watchdog.py) 的 `claim_single_instance()` |
| **复验** | **3 进程并发实测 → 1 True / 2 False**；`_claim_single` 改动量 20 行 → 34 行 |
| **可复用教训** | 「检查后创建」（TOCTOU）在进程治理里是经典陷阱 —— 该用**原子系统调用**，不要用应用层判断 |
