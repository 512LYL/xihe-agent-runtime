## 一、三通道终态与定位

| 通道 | 后端 | 接口 | 定位（冻结口径） |
|---|---|---|---|
| **①** | 云端 API：DeepSeek / 沐曦 **Qwen3.5-27B** | `https://ai.gitee.com/v1/chat/completions` | **多源韧性对照**（只作架构对照项陈述，**不用于实证数据**） |
| **②** | 本地 Ollama `qwen3.5:4b`（2.55 GB） | `http://127.0.0.1:11434/v1/chat/completions` | 断网兜底，**零成本** |
| **③** | **沐曦 C500 自部署 32B**（`xihe-32b`，vLLM 0.17.0） | 本机 `18000`（SSH 隧道）→ 实例 `8000` | **核心国产算力实证通道** |

**回落链**：`③ → ① → ②`（③ 不可达/超时/非 200 先回落 ①，绝不静默降到 ②）。

## 二、路由判定（三维度复杂度评估）

断网时，桥接器按三个维度判任务复杂度，**任一超标即判「复杂」**：

| 维度 | 阈值常量 | 值 | 理由 |
|---|---|---|---|
| 消息总 token 数 | `COMPLEX_TOKEN_THRESHOLD` | 4000 | 上下文长 → 4B 容易丢重点 |
| 工具数量 | `COMPLEX_TOOL_COUNT_THRESHOLD` | 2 | 多步操作 → 4B 工具能力弱 |
| 用户消息字符数 | `COMPLEX_MESSAGE_LENGTH` | 500 | 需求详细复杂 |

**复杂意图关键词**（命中任一即判复杂）：
`写一篇` / `生成PPT` / `总结这篇长文` / `写一个` / `生成报告` / `分析一下` /
`详细说明` / `详细解释` / `全面分析` / `帮我写`

### 决策表

| 场景 | 走哪条通道 | 说明 |
|---|---|---|
| 联网 + 点名 `model=xihe-32b` + ③ 在线 | **③** | 端到端实测 4.16 s |
| 联网 + ③ 在线 + 复杂任务/长上下文 | **③** | 复杂任务自动路由实测 19.68 s；桥接日志 `ROUTE: task COMPLEX + C500 alive → 通道③` |
| 联网 + 常规请求 | **①** | 云端主力 |
| 断网 + 简单任务 | **②** | 本地 4B 直接答 |
| 断网 + 复杂任务 | **暂停 + 续传** | 保存现场，后台每 30 s 探测网络，恢复后续传 |
| ③ 不可达 / 超时 / 非 200 | **①**（明确回落 + 告警） | ❌ 绝不静默降到 ② |
| 网络探测（`ai.gitee.com:443` TCP） | 1 秒结果缓存 + 3 秒超时 | 探测目标与云端 API 同域 |

## 三、协议适配与工具治理

| 后端 | 工具能力 | 桥接器动作 |
|---|---|---|
| 沐曦 27B（云端） | 支持 function calling | 保留全部工具（27 个） |
| 本地 4B（GGUF） | **不支持原生 `tools` 参数** | **剥离工具定义 → 注入 system prompt**，最多 4 个；优先 file / directory / list / read / write / search 类 |
| 通道③ 32B | 支持（需启动参数开启） | `--enable-auto-tool-choice --tool-call-parser hermes`；实测 `finish_reason = tool_calls` |

其它适配动作：
- **角色转换**：`tool` → `user`（前缀 `[Tool Result]`）；合并同角色连续消息；
- **语言绑定**：注入双语指令，避免本地模型回英文；
- **身份规则后缀**：注入「必须中文回复 / 不输出思考过程 / 不假装调用工具」；
- **多模态兼容**：`_inject_system_note()` 兼容 `str` 与多模态 `list`（修掉原 handler 对 list content 会 TypeError 的隐患）。

## 四、通道③ 的工程底座（生产参数）

### 4.1 硬件与实例

| 项 | 值 |
|---|---|
| GPU | **MetaX C500**；物理显存 65536 MiB（64G） |
| 切片 | **Vram Quota 32000 MiB（32G）、Compute 50%** |
| 软件栈 | **MACA 3.5.3.20**（驱动 3.8.30 / BIOS 1.33.5.0 / mx-smi 2.2.12） |
| 状态 | 33W/350W、33℃、P0、Available |

### 4.2 模型与推理

| 项 | 值 |
|---|---|
| 模型 | `Qwen/Qwen2.5-32B-Instruct-AWQ@master`（16 文件，AWQ 4bit，19 GB） |
| 部署路径 | `/models/Qwen2.5-32B-AWQ`（`Snapshot ready`） |
| 下载 | modelscope，分片 `model-0000x-of-00005`，12 ~ 34.6 MB/s（断点续传） |
| 引擎 | **vLLM 0.17.0**（沐曦版，`VLLM_USE_MXGPU=1`） |
| 启动 | `vllm serve /models/Qwen2.5-32B-AWQ --served-model-name xihe-32b --port 8000 --gpu-memory-utilization 0.85 --max-model-len 8192 --trust-remote-code` |
| 接入 | **SSH 固定隧道**：本机 `18000` → 实例 `8000`（取代了临时 ngrok 地址） |

### 4.3 上下文与显存账（为什么 32K 是合理上限）

| 窗口 | KV cache 需求 | 合计（+权重 ≈19 GiB） | 能否承载（32G 切片 ≈30 GiB 可用） |
|---|---|---|---|
| 16K | 4 GiB | ≈23 GiB | ✅ |
| **32K** | **8.44 GiB** | **≈27.5 GiB**（实测占用 29516/32000 MiB） | ✅ **本实例采用** |
| 64K | 16.9 GiB | 35.9 GiB | ❌ |
| 128K（模型原生上限） | ≈32 GiB | ≈51 GiB | ❌ |

> 结论：**不是模型上限（原生 131,072 tokens），而是显存不够** —— 32K 是 32G 切片下的合理上限。
> 单次生成上限 8192 tokens；KV cache 单位消耗 ≈ 256 KB / token。

### 4.4 超限前置拦截与无状态裁剪

| 项 | 值 / 做法 |
|---|---|
| 拦截阈值 | `C500_MAX_INPUT_TOKENS = 24000`（依据：32768 − 4096 输出预留 − 余量） |
| 超限实测 | 10000 中文字 ≈ 25010 tokens → **HTTP 400 + `code=input_too_long`** |
| 无状态裁剪实测 | 消息 4 → 2 条、6 → 2 条（system=1） |
| 副作用（如实写明） | 无状态模式**丢弃全部历史** → 无对话记忆，符合「单次重载任务」定位 |

> 2026-10-02 轮共 **33 个 400，全部是上下文超限**（28673+4096 > 32768，超 1 token），
> 属**客户端参数问题、非引擎缺陷**。网关侧 `contextWindow` 曾声明 40960（**虚高**，vLLM 实际 32768），
> 导致预算公式（`预算 = contextWindow/2`）算出 20480 才勉强通过 —— 这类「声明值 vs 实际值」不一致已登记。

### 4.5 探活与报警（`c500_watchdog` 系列）

覆盖三类场景：**实例失联 / 隧道地址漂移 / 忘关机**。

| 参数 | v1.0 | v1.3（现行） |
|---|---|---|
| 轮询间隔 | 120 s | 120 s |
| 启动延迟 | 2 轮（≈4 min） | 2 轮 |
| 判定失联 | 连续 2 轮（≈4 min） | **连续 3 轮（≈6 min）**（避开 vLLM 重启加载窗口 ≈85 s 的误报） |
| 报警冷却 | 30 min | 30 min |
| 恢复冷静期 | 10 min | 10 min |
| 全局配额 | 3 封/小时 | 3 封/小时 |
| 自动退出 | 20 轮（≈40 min） | 20 轮 |
| 闲置提醒 | 30 min 无推理请求 | 30 min |
| 通知链路 | 邮件（SMTP）+ 桥接 `/send` 直发 —— **均不经模型、零推理消耗** | 同 |

其它：`c500_watchdog.py` 511 → 564 行；参数单测 9/9 → 6/6 通过；修复重复发送隐患 4 个、深层漏洞 1 个（`ever_online`）。

## 五、成本口径（★ 必须双口径，否则数字互相打脸）

| 口径 | 值 | 说明 |
|---|---|---|
| **单价** | **2.50 元 / 小时** | C500 32G 实例按小时计费；用即烧钱、关机即停 |
| **券消费总额** | **122.61 元** | 09-21 余额 239.60 → 10-11 余额 116.9917 ⇒ 区间消耗 122.61 元 ≈ **49.04 h 机时** |
| **当前实例机时** | **20 h 29 m** | 折 **51.21 元** |
| **差额** | **71.40 元 ≈ 28.56 h** | **原因未验证**（可能另有实例开关机 / 两轮压测用机未计入 / 券发放折旧规则） |

> ⚠️ **申报材料若同时出现「花费」与「运行时长」，必须注明口径**（券消费总额 vs 当前实例机时）。
> 另：09-21 存在两个不同余额数（239.60 vs 251.8）→ **以本台账 239.60 为准**，其余标注来源。
>
> 被否决的成本方案（写进材料可体现取舍）：
> 早期按 7×24 常驻监控设计会产生**成本悖论** —— 管家常驻 → 实例必须常开 → **60 元/天**，
> 而管家的职责恰恰是「不让 C500 白烧钱」。改为**任务执行期监工**后，管家与任务同机同时，
> **边际成本 ≈ 0**，悖论消除。
>
> **成本不是唯一理由，方向才是**：陌生人通道走本地「不只是省钱，而是**默认让陌生人的内容留在本地**；
> 宁可多试一次本地，也不轻易把内容发给云端。**成本是次要的，方向才是第一位的。**」
